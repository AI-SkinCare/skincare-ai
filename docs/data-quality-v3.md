# 성분 추천 데이터 품질 개선 — v3

2026-10-02, `feat/rec-sllm-v2` 작업 폴더에서 원본 라벨 9,000건을 검사하고 별도 v3 데이터를 생성했다. 이번 결과는 **데이터 처리와 평가 기준의 개선**이다. v3 모델 재학습·GPU 추론 성능 검증은 아직 하지 않았다.

## 팀에 전달할 설명

> 기존 데이터에서 서로 다른 식물과 부위의 성분명이 하나로 합쳐지고, 정제 과정에서 영문 성분명이 지워지는 문제가 있었습니다. 이름 사전과 정제 코드를 수정하고, 정제 전후 성분이 보존되는지 검사하도록 했습니다. 원본 9,000건 중 입력 고민 불일치, 한글·영문 성분 충돌, 의료 표현 등 검토가 필요한 430건은 자동으로 정답을 추측하지 않고 별도 격리했습니다. 학습 7,564건(고유 7,548건), 개발 검증 144건, 새 실험용 시험 후보 525건으로 나눴으며, 세 분할 사이 동일 입력·정답 겹침은 0건입니다. 채점은 추천 성분이 적어도 precision@3 분모를 항상 3으로 고정하고, 다른 데이터·사전·채점 기준의 결과는 비교하지 못하게 했습니다. 전문가의 효능 검토와 희소 고민 신규 데이터 확보가 남아 있으며, 모델 성능 개선 여부는 재학습 후 같은 문항으로 비교해야 합니다.

## 무엇을 바꿨는가

| 문제 | 처리 | 재발 방지 |
|---|---|---|
| 서로 다른 영문 성분이 공유 한글 이름을 통해 합쳐짐 | 같은 영문 이름 안에서만 별칭을 묶고 다의적인 연결자는 제외 | 서로 다른 영문 이름을 잇는 한글 별칭 회귀 테스트 |
| 카멜그라스가 대나무로, 리치 열매가 씨앗 가루로 매핑 | 식물·부위별 이름 분리. 이름 교정 목록을 코드에 명시 | 잘못된 구사전으로도 교정되는지 검사 |
| 일반 `ROOT EXTRACT`, `SEED EXTRACT` 및 복합 성분 목록을 단일 성분으로 매핑 | 종을 모르는 일반 이름과 합쳐진 영문 키 제거 | 모호한 키를 정답으로 채점하지 않는 테스트 |
| 숫자 포함 성분 누락 | 헥사펩타이드-11, 3-o-에틸아스코빅애씨드, 1-메틸하이단토인-2-이미드 등 추가 | 숫자 경계 검사: 미등록 `헥사펩타이드-111`을 11로 채점하지 않음 |
| `(SULFUR)는`이 `는`만 남는 오류 | 한글명이 없으면 삭제 대신 `(유황)은`으로 변환 | 단독 괄호·조사·별칭·대표명 공백 테스트 |
| 한글·영문 병기가 서로 다른 성분 | 자동으로 한쪽을 선택하지 않고 격리 | 충돌 원문을 검토 목록에 보존 |
| 3·4단계 혼재, 단계 제목 변형 | 3단계 제목/번호로 통일. 추가 단계 내용은 3단계에 합쳐 보존 | 단계 내용 보존 테스트 |
| 의료 표현을 단순히 `치료→관리`로 바꾸면 사실 확인처럼 보임 | v3에서는 해당 원문을 먼저 격리. 기존 cleaner의 표현 치환은 효능 검증으로 간주하지 않음 | 원문 기준 의료·보톡스 표현 검사 |
| `탁월한`, `효과적입니다`가 기존 필터를 통과 | 정제·서빙 공통 표현 완화 규칙 보강 | 문구 완화는 과학적·법적 적합성을 보증하지 않음 |
| 복제된 표본이 사전/빈도에 영향을 줄 수 있음 | 기존 `#dup` 제거 후 사전·빈출 성분 생성 | 검증 데이터가 사전/학습 빈도를 바꾸지 못하는 테스트 |
| 검증에서 학습과 동일한 입력을 반복 채점 | 코드·추가 질문을 제거한 실제 서빙 입력 기준으로 그룹 분리. 고민/외부 요인 순서 차이도 같은 그룹으로 판단 | 분할 간 입력·정답 겹침 시 검사 실패 |
| 성분 1개를 맞히면 precision@3가 100%가 됨 | 맞힌 수/3으로 고정: 1개 정답이면 33.3% | 모델 점수·폴백 점수를 분리한 회귀 테스트 |
| 이전 결과와 새 결과 혼합 | 모집단·사전·채점·입력 정책·필터·프롬프트 지문 기록. v3 결과 폴더 분리 | 기준이 다르면 비교표 생성 거부 |

한글 대표명은 프로젝트 내부 비교용 이름이다. 위 변경은 **성분의 이름 동일성을 정리한 것**이며 효능·사용 안전성에 대한 승인이 아니다. 기존 v1/v2 데이터 파일·어댑터·평가 결과는 보존했다. 실행 시 구사전을 교정해서 읽기 때문에 새 추출 결과는 과거 저장 점수와 달라질 수 있다.

## 실제 생성 결과

| 항목 | 건수 |
|---|---:|
| 원본 학습 / 검증 | 8,000 / 1,000 |
| 검토 격리 — 학습 / 검증 | 376 / 54 |
| 격리 합계 | 430 |
| 정제 후 중복 정답 제거 — 학습 | 76 |
| 입력 겹침 제외 — 개발 검증 / 시험 후보 | 46 / 231 |
| 최종 고유 학습 | 7,548 |
| 제한적 복제 포함 학습 | 7,564 |
| 개발 검증 `val_eval` | 144 |
| 시험 후보 `test` | 525 |

격리 사유는 의료·보톡스 표현 342건, 한글·영문 성분 충돌 73건, 성분 추출 불가 8건, 입력 고민 불일치 9건이다. 사유가 겹치는 표본이 있어 합계를 더하면 430건보다 크다. 의료 표현 탐지는 보수적인 문자열 검사이며 전문의 상담 안내 등도 포함할 수 있다. 격리는 잘못된 효능이라는 판정이 아니라 **사람이 확인할 때까지 학습에서 보류**하는 조치다.

희소 고민은 과각질 49건, 탄력 저하 42건, 민감성 7건의 고유 학습 표본만 있다. 복제는 최대 2배, 50건까지만 적용했다. 민감성 14행은 14개의 새 사례가 아니라 7개의 원본과 7개의 사본이다. 클래스 불균형을 해결했다고 발표하면 안 된다.

기본 서빙 입력에서는 상태 코드와 추가 질문을 쓰지 않으므로 v3 학습도 두 필드를 제거했다. 여전히 같은 입력에서 다른 정답 성분 집합을 가진 학습 그룹 548개, 1,287행이 남는다. 유효한 대안 추천일 수도 있고 입력 특징이 부족한 것일 수도 있어, 자동으로 잘못된 라벨이라고 판단하지 않았다. `ambiguous_input_groups.json`에서 별도로 검토할 수 있다.

## 출처 품질과 효능 검토

원본 9,000건 중 **최소 3,357건(37.3%)**이 `12345678|10\.xxxx|xxxxx|10\.1234/example|placeholder` 검사에 해당한다. 기존 문서의 “약 75%” 표기는 근거가 확인되지 않아 수정했다. 나머지 62.7%의 출처가 검증됐다는 뜻은 아니다.

`PMID:12345678`은 실제 PubMed 항목이지만 피부 성분 효능 논문이 아닌 인구·개발 선언문이다. [PubMed 원문 정보](https://pubmed.ncbi.nlm.nih.gov/12345678/)를 확인할 수 있다. 자리표시자를 찾지 못했다고 올바른 효능 근거가 되는 것은 아니다. 모든 유지 표본에 `efficacy_not_expert_verified` 표시를 넣었다.

출처 문제가 있는 모든 표본을 자동 삭제하지는 않았다. 전체의 상당 부분을 출처 문자열만으로 지우면 고민 분포가 다시 바뀌고, 성분 추천 자체의 정오를 확인한 것도 아니기 때문이다. 출처는 학습 출력에서 제외하고 검토 목록에 원문과 함께 보존했다. 최종 제품 적용 전에는 성분-효능·농도·사용법·피부 자극 가능성을 전문가가 검토해야 한다.

## 검증 결과와 해석

- 전체 pytest **81개 통과**. 이름 교정, 성분 보존, 분할 겹침, 검증 정보 유출, 평가 기준 혼합 방지, 서버 회귀 검사 포함.
- v3 전체 8,233행 검사 통과: 분할 간 동일 입력 0건, 동일 정답 0건, 정제 중 성분명 누락 0건, 저장 정답 성분과 재추출 불일치 0건.
- 같은 원본으로 재생성할 때 데이터·목록·보고서의 바이트 동일성 검사 수행. `manifest.json`에 원본·처리 코드·사전·필터·분할 해시를 기록했다. 기존 목적지의 내용이 달라지면 생성기가 새 `--dst` 사용을 요구한다.
- Qwen2.5-7B의 로컬 토크나이저로 검사했다. v3 학습 길이는 p50 1,406, p95 1,755, 최대 2,446토큰. 2,048토큰 초과 46행은 기존 trainer 정책대로 통째로 제외하며 JSON을 자르지 않는다. 따라서 실제 학습 예정은 **7,518행**이다. 개발 검증은 길이 초과 0행이다.
- 같은 토크나이저로 재측정한 v2는 8,258행 중 길이 초과 182행, p95 1,905, 최대 2,667토큰이었다. v3에서는 추가 질문·코드를 제거하고 표본을 격리·정제했기 때문에 길이가 줄었다. 동일 모집단에 대한 성능 개선 수치로 해석하지 않는다.
- 시험 후보의 길이 초과 1행은 학습 길이 기준의 참고 수치다. 추론 평가는 정답을 입력으로 넣지 않으므로 이 이유로 시험 문항을 제외하지 않는다.
- 개발 검증 144건의 규칙 기준선: 고정 precision@3 **69.91%**, 고민별 동일 가중 평균 **64.49%**, 정답 추론문 글자 2-gram F1 **0.162**. 시험 후보의 성능은 계산하지 않았다.

기존 v2의 78.36%와 이 수치를 직접 비교하면 안 된다. 모집단, 성분 사전, 정답 추출, precision 분모, 필터가 바뀌었다. 과거 결과에는 모든 생성 원문이 저장되어 있지 않아 기존 `pred` 목록만으로 새로운 사전의 누락 성분을 복구할 수도 없다. 같은 v3 개발 문항에서 규칙·원본 모델·v2·v3을 다시 생성해 비교해야 한다. 앞으로는 모든 문항의 원문·파싱 결과·필터 후 답변·정답을 저장한다.

**시험 후보 525건은 완전한 외부 독립 시험이 아니다.** 원본 검증 전체는 과거 v1/v2 실험에서 이미 평가됐다. 이번 v3 학습·개발 검증에서 따로 보관하는 내부 시험 후보이며, 확증 성능 발표에는 새로 수집한 시험 세트가 필요하다. 과각질·민감성·홍조·탄력 저하 4종은 기존 개발 검증에 전부 포함돼 있어 이 후보에 0건이다. 이 후보의 평균으로 8종 전체 성능을 주장하면 안 된다. 복합 고민 데이터도 정답은 주 고민 하나 기준이라, 여러 고민을 모두 적절히 다뤘는지는 별도 평가가 필요하다.

## 재현 방법

`AI` 레포 루트 PowerShell, 기존 학습용 가상환경 기준이다. 데이터와 모델은 Git 제외 대상이며 팀원은 원본 데이터 경로를 지정해 재생성한다.

```powershell
# v3 생성 및 무결성·성분 보존 검사 (GPU 불필요)
.\.venv\Scripts\python.exe -m src.llm.prepare_quality_data
.\.venv\Scripts\python.exe -m src.llm.audit_quality_data

# 로컬에 저장된 Qwen2.5 토크나이저로 길이까지 검사 (GPU·다운로드 불필요)
.\.venv\Scripts\python.exe -m src.llm.audit_quality_data --tokenizer outputs/rec_sllm_v2/adapter

# 개발 검증만 사용한 규칙 기준선 및 비교표
.\.venv\Scripts\python.exe -m src.llm.evaluate --config configs/sllm_qlora_v3.yaml --mock
.\.venv\Scripts\python.exe -m src.llm.compare --eval-dir outputs/eval/sllm_v3/val_eval
.\.venv\Scripts\python.exe -m pytest -q
```

원본 경로를 변경할 때는 `prepare_quality_data --raw-root "…/2.데이터(NIA)"`를 사용한다. 토크나이저가 없으면 `audit_quality_data`의 기본 검사는 그대로 가능하다. 모델 ID로 길이를 검사하려면 올바른 `HF_HOME`을 지정하거나 로컬 토크나이저 디렉터리를 전달한다. v3 기본 설정은 일반 `prepare_data`용 설정이 아니며 **`prepare_quality_data`로 생성**한다. `run_pipeline.bat`의 기존 v2 실행을 새 데이터 생성 명령으로 대체하지 않는다.

## 다음 GPU 실험

이번 작업에서는 아래 장시간 작업을 시작하지 않았다. v1/v2 서비스 결과와 v3 성능을 비교하려면 이 순서로 진행한다.

```powershell
$env:HF_HOME = "D:/hf_cache"
$env:PYTORCH_CUDA_ALLOC_CONF = "max_split_size_mb:128"

# 원본 / v2 비교는 같은 v3 개발 문항으로 다시 생성
.\.venv\Scripts\python.exe -m src.llm.evaluate --config configs/sllm_qlora_v3.yaml --base Qwen/Qwen2.5-7B-Instruct
.\.venv\Scripts\python.exe -m src.llm.evaluate --config configs/sllm_qlora_v3.yaml --adapter outputs/rec_sllm_v2/adapter

# 모델 서버 등 GPU 사용 프로세스를 종료한 뒤 별도 v3 어댑터 학습
.\.venv\Scripts\python.exe -m src.llm.train_qlora --config configs/sllm_qlora_v3.yaml
.\.venv\Scripts\python.exe -m src.llm.evaluate --config configs/sllm_qlora_v3.yaml --adapter outputs/rec_sllm_v3/adapter
.\.venv\Scripts\python.exe -m src.llm.compare --eval-dir outputs/eval/sllm_v3/val_eval
```

모델 선택이 끝난 후에만 `--split test`를 사용한다. 시험 결과를 보고 모델·데이터를 계속 고치면 다시 개발 검증이 된다. v3 어댑터 검증 전에 서버 기본 어댑터를 교체하지 않는다. 기존 `.bat`의 중단 감지/재시도는 이 직접 실행 명령에 적용되지 않으므로 학습 로그와 체크포인트를 확인해야 한다.

## 산출물과 팀에 필요한 후속 작업

- `data/processed/sllm_v3/quality_report.json`, `audit_report.json`: 실제 건수·분할·길이·검사 결과.
- `manifest.json`: 재현 및 비교 기준 식별자.
- `quarantine.jsonl`: 보류한 430건의 원문, 입력, 사유, 출처.
- `review_queue.jsonl`: 유지 표본의 효능·출처·희소 고민·복합 고민 검토 목록. `review_priority` 0부터 확인한다.
- `ambiguous_input_groups.json`: 같은 서빙 입력에서 다른 정답을 가진 학습 그룹의 원본 ID.
- `outputs/eval/sllm_v3/val_eval/`: 모든 문항별 생성 결과와 비교표.

팀에 요청할 후속 작업은 (1) 격리 표본의 정답/성분명 전문가 검토, (2) 희소 고민 4종의 **다른 사용자 프로필과 정답** 확보, (3) 복합 고민 답변의 전체 고민 충족 여부 평가, (4) 출처가 실제 성분·농도·효능 주장을 뒷받침하는지 확인이다. 기존 사례 복제나 문장만 바꾼 합성 데이터를 독립적인 새 표본으로 세지 않는다.
