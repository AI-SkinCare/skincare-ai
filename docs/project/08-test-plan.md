# 테스트 계획서

**문서 번호** SC-08 · **버전** v1.0 (2026-10-01) · **작성** 김우주 · **관리** 손승우

## 1. 목적 · 범위

[요구사항 정의서](01-requirements.md)의 기능(FR)·비기능(NFR)·모델 성능(MR) 요구사항이 충족되는지 확인하는 방법과 기준을 정합니다. 질환 진단처럼 범위에서 제외한 기능은 "하지 않는지"를 확인합니다(TC-REG).

## 2. 테스트 레벨

| 레벨 | 대상 | 도구 | 담당 | 시점 | 자동화 |
|---|---|---|---|---|---|
| 단위 | 함수·서비스·컴포넌트 | Vitest(FE), Jest(BE), pytest(AI) | 각 레포 담당 | 개발 중 상시 | CI |
| 계약 | 백엔드 ↔ AI 응답 구조 | Jest + fixture JSON | 이현승, 김우주 | AI 응답이 바뀔 때 | CI |
| API 통합 | 백엔드 + DB | Jest e2e (supertest) + PostgreSQL 컨테이너 | 이현승 | PR마다 | CI |
| E2E | 브라우저 전체 흐름 | Playwright (모바일 뷰포트 390×844) | 정도희 | M2 이후 주 1회, 발표 전 | 수동 실행 |
| 3계층 통합 | 프론트 + 백엔드 + 실제 AI 서버 | 체크리스트 (§4) | 전원 | 11/10 – 11/24, 발표 전날 | 수동 |
| 성능 | 응답 시간, 동시 요청 | k6 | 이현승, 김우주 | 11/10 – 11/20 | 스크립트 |
| 모델 평가 | MR-01 ~ MR-08 | 평가 스크립트 (`skincare-ai`) | 김우주, 박성근 | 모델 갱신 시 | 스크립트 |

현재 `skincare-ai`에는 GPU 없이 도는 pytest 68개가 있습니다(10/1 기준, 전부 통과).

## 3. 테스트 환경

| 환경 | 구성 | 용도 |
|---|---|---|
| 로컬 | 백엔드 `AI_MODE=fixture` + 로컬 PostgreSQL | 단위·통합·E2E 대부분 |
| 스테이징 | 정도희 서버 배포본 + 김우주 PC AI 서버(`REC_BACKEND=sllm`) | 3계층 통합, 성능, 시연 리허설 |
| 테스트 계정 | `test01~test40@skincare.dev` (시드, `test01`은 완료 분석 25건 보유) | 동시 요청·대기열·이력 테스트 (사용자당 진행 중 분석 1건 제한 때문) |
| 제한 값 | 스테이징 성능 테스트 동안 `ANALYSIS_DAILY_LIMIT=100`. 부하 스크립트는 계정별 토큰을 미리 발급해 로그인 제한에 걸리지 않게 함 | |
| fixture 시나리오 | `AI_FIXTURE_SCENARIO` 또는 `X-Fixture-Scenario` 헤더 ([API §7](03-api-spec.md#7-개발용-고정-응답-fixture)) | 실패·지연 재현 |
| 테스트 이미지 | 공개 데이터의 정면 얼굴 샘플, 얼굴 없는 사진, 흐린 사진, 11MB 파일, GIF | §4 케이스 |

실제 사람 얼굴 사진은 팀원 본인이 동의한 것만 쓰고, 레포에 커밋하지 않습니다.

## 8. 결함 관리

- 결함은 버그 템플릿으로 해당 레포에 이슈를 엽니다(재현 절차, 기대·실제 결과, 요청 ID, 화면 캡처).
- 심각도: `P0` 시연·핵심 흐름 차단 → 당일 수정 / `P1` 기능 일부 오동작 → 이번 마일스톤 / `P2` 표시·문구 → 여유 시.
- 수정 PR 본문에 `Fixes #이슈번호`를 적어 자동으로 닫습니다. 수정 후 해당 테스트 케이스를 다시 실행해 결과 열을 갱신합니다.
